- Hardware: Apple M4 Max, 16 logical CPUs, 64 GiB RAM (macOS)

## B1: commit to client latency

Table `bench` with 1000 rows, 10 clients, one writer at 100 txn/s for 30 s (ran 30.0 s). Each txn updates one random row; `sent_us` is taken right before the `BEGIN; UPDATE; COMMIT` round trip. A client's latency for a row is measured when the `commit` event that carries the row arrives.

|---|---|---|---|---|
| commit sent → commit event received | 2.56 | 5.15 | 7.22 | 25.19 |
| writer COMMIT round trip | 1.60 | 3.45 | 5.28 | 18.33 |

Updates written: 3000. Updates received per client: [3000, 3000, 3000, 3000, 3000, 3000, 3000, 3000, 3000, 3000] (all equal to written). Latency samples: 30000.

## B3: catch-up cost

Table `bench_big (id bigint pk, payload text)` with 100000 rows of about 200 bytes of payload. Time is measured inside the client, from sending the request until the `commit` event has been read. Bytes are the SSE bytes consumed up to and including that event. A full catch-up was run once beforehand and discarded (warm-up). The change set is one transaction: 70 updates, 20 deletes, 10 inserts (100 rows). Rows events are parsed after the clock stops.

| (a) full catch-up, no offset | 85.5 | 20.68 MiB | 100000 / 0 / 0 | 1 | 0 / 0 / 1 | 0 | 0 / 100000 | 1 | 69.4 | 100000 |

## Observations

- **Latency (B1):**
  - Commit → client is p50 2.6 ms and p99 7.2 ms, against targets of 25 ms and 100 ms.
  - The measured span includes the writer's own `COMMIT` round trip (p50 1.6 ms), so the engine's share is about 1 ms.
  - The machine is noisy: other B1 runs gave a p50 of 0.85 and 2.1 ms.
- **Ingest (B2):**
  - The engine sustains about 22.5k row changes/s against the 10k target. It trails by at most 14.8 MiB of WAL and drains 0.57 s after the writers stop.
  - Group commit batches only 3.6 transactions per store commit here. macOS SQLite doesn't use `F_FULLFSYNC`, so fsync is cheap on this machine; a Linux run with real fsync will tell whether batching keeps up.
- **Catch-up (B3), matching ADR 0001's prediction:**

  | Resume | Time | Bytes | Postgres execution |
  |---|---|---|---|
  | Delta (100 changed rows) | 2.4 ms | 20 KiB | 0.6 ms |
  | Forced full | 84 ms | 20.7 MiB | 68 ms |
  | Nothing changed | 0.5 ms | — | no query |

  The delta is about 1,000× fewer bytes and 110× less Postgres time than the forced full.
- **Engine gaps these runs exposed** (not fixed):
  - The `server_wal_end − applied_lsn` lag metric understates lag (11 KiB vs 14.8 MiB). Lag should be measured against `pg_current_wal_lsn()`.
  - PLAN §9's store-commit-latency, catch-up-duration and Postgres-read-time histograms don't exist yet.
  - The live path sends one `commit` event per transaction (715k events, 141 MiB in B2). A client that is behind gets no coalescing.
